## 2. Architecture decision

**Chosen approach: "Policy-by-default + explicit trust roots."**

1. **RBAC enforcement becomes profile-independent.** The PEP is registered on *all three* profiles via their `cordis.patch.yml`, and the container **fails to boot** if the active profile lacks a working policy engine. A test asserts parity. (Fixes V3-H1.)
2. **A persona's `rbac:` block becomes a validated contract, not optional prose.** A JSON schema + `resolveEffectivePolicy()` fails closed; templates and `distillPersona` always emit the contract. (Fixes V3-H2, hardens H-4.)
3. **Approval verification gets one canonical trust root** at `/etc/dsh/keys/approval_ed25519.pub`, wired by the installer, with checkpoint `status` bound into the token digest so a consumed checkpoint can never be resurrected. (Fixes R-2, H-3.)
4. **One authorization gate for every step, including fallbacks**, and write/execute actions default to gated. (Fixes V3-M6, V3-M7, TQ-2.)
5. **Installer and provisioning are driven by one manifest**, `.env` is allowlisted, and fallback downloads are hash-verified or refused. (Fixes H-1, H-2, R-1, R-4.)

**Rationale:** every fix rides an existing abstraction (patch insert, policy codes, token verifier, installer generator) — no new runtime dependencies, no framework change. The one structural addition (boot assertion + provisioning manifest) converts repeated "someone forgot to wire it" failures into build/boot failures.

**Trade-offs (accepted):**
- Adding `@dsh-dds/core` to `cli`/`headless` increases their plugin surface; acceptable — the core is policy-only and has no network/UI.
- Boot assertion can break a misconfigured deployment; that is the point (fail closed).
- Binding `status` into the digest invalidates pre-upgrade tokens; documented as a one-time migration.

## 5. Data flow

**Interactive tool call (chat):**
`harness tool-execute` → Cordis waterfall `tools/pre-execute` → `preExecuteWaterfall(exec,next)` (`rbac-interceptor.js:247`) → build `actionContext` with `persona` → `resolveUser` (IAM or fail closed) → `validatePathAccess` tenant check (`:139`) → `resolveEffectivePolicy(meta)` → `enforceRbacPolicy(meta, step)` → GRANT: fail-closed audit + issue capability → `next()`; DENY/GATE: best-effort audit + `{kind:'deny'}`.

**Declarative step (workflow):**
`runWorkflow` → `executeStep` → normalize → `authorizeStep` (RBAC + gate) → frozen envelope → handler → on failure `triggerFallback` → **fallback re-enters `authorizeStep`** → loop trap checks bounded ring → output.

**Approval lifecycle:**
gate → checkpoint `SUSPENDED_APPROVAL_REQUIRED` (atomic temp+rename) → host `dsh.sh approve` signs Ed25519 token over `{instanceId, stepIndex, status, checkpointDigest}` → container `verifyApprovalToken` reads `/etc/dsh/keys/approval_ed25519.pub` → status must be `SUSPENDED` and `consumedAt` null → transition `IN_PROGRESS` → execute → on new gate write **only** the new checkpoint; old one → `CONSUMED`.

**Install:**
`install_dsh.sh` → allowlisted `.env` load → `provisioning-manifest.mjs` → archive fetch **or** per-file verify → hash gate → staged promote → keygen → write `DSH_APPROVAL_PUBLIC_KEY` + `chmod 0600 .env`.

## 7. Critical details

**Error handling.** Reuse `RBAC_*` codes; new codes `RBAC_PERSONA_UNRESOLVED`, `RBAC_MANIFEST_INVALID`, `APPROVAL_CHECKPOINT_CONSUMED`. Denials stay best-effort-audited; grants fail closed (`orchestrator:1159`). Installer integrity failures abort the install — no `|| true` on hash checks.

**State management.** All checkpoint writes become atomic temp+rename+fsync (match `audit-writer-core`). Checkpoint status is a monotonic state machine: `SUSPENDED → IN_PROGRESS → CONSUMED|FAILED|EXPIRED`; no reverse transitions.

**Testing.** One test file per component (list above), each with negative cases first: planted `.env` must not be honored; ungoverned profile must fail the parity test; consumed token must be rejected; `A,B,A,B` must trap; fallback must re-gate. Add `setup-node` matrix (Node 22/24) and a CI step running `envoy --mode validate`.

**Performance.** Policy resolution is in-process and O(1); memoize `resolveEffectivePolicy` per persona name. The loop-ring is capped at 8 (was unbounded growth).

**Security.** No new dependencies (uses existing `yaml`). Manifest values never interpolate into YAML raw. Key material never enters the build context. The `apply_fix_or_patch` gate default closes the human-checkpoint gap without breaking existing single-gate workflows.

**Migration.** Digest binding invalidates outstanding approval tokens on upgrade — document as a breaking change in `CHANGELOG.md`; existing suspended checkpoints must be re-approved once.

## 8. Reconciliation notes — 12 September 2026

The original blueprint was compared with the current repository before implementation. Two design assumptions were corrected:

* the synthetic interactive persona cannot yet be removed because the proposed `persona-registry` service does not exist; explicit persona propagation must be designed first; and
* approval public-key discovery should use the canonical mounted file or a `DSH_APPROVAL_PUBLIC_KEY_FILE` path, not embed PEM text directly in `.env`.

Phase 1 deliberately lands only the verified profile-enforcement slice. It does not claim the boot assertion complete. Phases 2–7 remain open, including the confirmed multi-gate checkpoint replay flaw and installer environment-loader hardening.
